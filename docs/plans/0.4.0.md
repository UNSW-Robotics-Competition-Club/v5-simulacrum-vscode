# 0.4.0 implementation plan: Rust (vexide) and Debug on Sim

Status: draft, 2026-11-20. Spans two repos: this extension and the simulator
(`v5-simulacrum`). The simulator's `main` must land first: the bundle workflow
builds the runtime from it.

## Goals

1. **vexide (Rust) projects** run on the simulator like VEXcode and PROS
   projects: detected, offered after a build, Run on Sim, uploaded with
   `cargo v5 upload` where a Windows program can reach the brain.
2. **Debug on Sim**: F5 on a vexide or PROS project that uses
   [v5gdb](https://github.com/vexide/v5gdb) starts the simulator with the
   program and attaches GDB: breakpoints, stepping, variables, call stack.
3. Carry-overs: active users per version (`feat/active-users`), the VEXcode
   port note.

Not in 0.4.0: debugging VEXcode programs (v5gdb doesn't support them);
QEMU's own GDB stub (pausing the CPU pauses VEXos while the robot sim runs
on); LLDB; vexide differential uploads beyond checking
they work over `cargo v5 upload`.

## What we know (sources)

- **cargo-v5** (0.12.1, [build.rs](https://github.com/vexide/cargo-v5/blob/main/src/commands/build.rs),
  [metadata.rs](https://github.com/vexide/cargo-v5/blob/main/src/metadata.rs),
  [upload.rs](https://github.com/vexide/cargo-v5/blob/main/src/commands/upload.rs)):
  - The default target is `thumbv7a-vex-v5`; a project can set
    `armv7a-vex-v5`, which v5gdb's docs use.
  - The `.bin` sits next to the ELF: `target/<triple>/<profile>/<name>.bin`,
    and the ELF is `target/<triple>/<profile>/<name>` with no extension.
  - `[package.metadata.v5]` keys: `slot` (1–8), `icon`, `compress`,
    `upload-strategy` (`monolith` | `differential`).
  - A differential upload keeps a local `slot_N.base.bin` next to the build;
    on the brain it writes `slot_N.base.bin`, plus `slot_N.bin` as a gzipped
    patch linked to the base at 0x07A00000.
- **v5gdb** (release v0.1.0-beta.2; wiki: Transports, Installation and setup
  for Rust and for C++, Debugging in VS Code):
  - Supports vexide ≥ 0.9.0-alpha.1 (`cargo add v5gdb`,
    `v5gdb::install(V5Debugger::stdio())`) and PROS ≥ 4.2.3
    (`pros c apply v5gdb` from its depot, `v5gdb::install({...})` in
    `initialize()`). Not VEXcode.
  - Brain → PC: COBS-encoded packets of at most 2048 bytes; the first byte is
    the channel: `d` debugger (GDB RSP), `l` log (UTF-8), `u` user output.
    Invalid packets and unknown channels count as user output.
  - PC → brain: raw bytes, all of them treated as debugger (GDB RSP) data.
  - Host CLI `v5gdb [ELF] [--tcp=ADDR]` serves GDB on TCP (35537 by
    default). It needs the brain on USB, as the only program using it.
  - VS Code recipe: `cppdbg` with `miDebuggerServerAddress`,
    `stopAtConnect`, and these setup commands:
    `mem 0x100000 0x2c00000 ro cache`, `mem 0x2c00000 0x8000000 rw cache`,
    `set dcache line-size 1024`; plus `add-symbol-file bin/cold.package.elf`
    for PROS hot/cold.
  - GDB: the PROS toolchain's `arm-none-eabi-gdb` (already installed with
    the PROS extension: `globalStorage/sigbots.pros/install/pros-toolchain-windows/usr/bin/arm-none-eabi-gdb.exe`),
    `gdb-multiarch`, Homebrew `gdb`, or msys2 `gdb`.
- **Simulator**:
  - It already models the A9 debug hardware v5gdb uses
    (`qemu-vex/patches/0006-a9-debug-rom-mmio.patch`; `SIMULATOR.md` §5).
  - The brain's USB user port is a QEMU unix socket, `$T/v5usb-user.sock`.
    `v5usb_pty.py` (`--usb`) or `v5usb_usbip.py` (`--usbip`) is its one
    client.
  - The bundled runtime copies every non-test `scripts/*.py`
    (`bundle/build-runtime.sh`), so a new script ships with no bundling
    change.

Spike results (2026-11-20):
- **COBS delimiter:** 0x00, confirmed in v5gdb's CLI (`cli/src/serial.rs`:
  "Zero bytes are frame delimiters"). It decodes with a 2048-byte buffer.
  Channels are `u`, `d`, `l`; anything else goes out as raw user output.
  The CLI's TCP default is `127.0.0.1:35537`.
  - Also there: `cli/src/serial/pros.rs` decodes PROS's own output framing
    (COBS, a 4-byte stream id `sout`/`serr`/`kdbg`/`jinx`, frames up to
    0x4000). Use it as the reference for a 0.5 PROS decoder.
- **Build target:** vexide's template sets no target (`.cargo/config.toml`
  only has link args and `build-std`), so `cargo v5 build` uses
  `thumbv7a-vex-v5`. Check both triples anyway, since v5gdb's docs use
  `armv7a`.
  - Not confirmed by a real build yet: building a cloned project here was
    blocked. Confirm on a real vexide project.
  - The template defaults to `upload-strategy = "differential"` and
    `vexide = "0.8.0"`. So B3 (differential over usbip) matters for most
    Rust users, and most template projects fail v5gdb's
    vexide ≥ 0.9.0-alpha.1 gate (C2 step 2 warns).
- **Debug type switch:** VS Code allows it.
  - `resolveConfigurationByProviders` (`debugConfigurationManager.ts`)
    loops: when a provider returns a different `type`, it runs that type's
    `resolveDebugConfiguration` too. Then
    `resolveDebugConfigurationWithSubstitutedVariables` runs for the new
    type only (`debugService.ts`).
  - So C4's work goes in **`resolveDebugConfiguration`**, not the
    `WithSubstitutedVariables` hook (ours would never be called). It
    returns a `cppdbg` config with absolute paths. The fallback isn't
    needed.
- **WSL localhost:** a TCP server on `127.0.0.1` inside WSL2 (NAT mode,
  no `.wslconfig`) is reachable from Windows at `127.0.0.1`. Mirrored
  networking is untested.

## Workstream A: vexide projects (extension)

### A1. Detect a vexide project (`src/programs.ts`)
- **`cargoProject(root, fs)`:** reads `Cargo.toml`. It's a vexide project
  if `[dependencies]` names `vexide`, or if `[package.metadata.v5]` exists.
  The label is `Rust project <package.name>`, the slot comes from
  `metadata.v5.slot` (1–8), and `program` is the newest
  `target/{thumbv7a,armv7a}-vex-v5/{debug,release}/<name>.bin` (by mtime).
- **TOML:** a small line-based reader in `programs.ts` for the four keys
  we need (`[package] name`, `[package.metadata.v5] slot`, the `vexide` and
  `v5gdb` dependencies, `.cargo/config.toml` `[build] target`). No new
  dependency: the package is built with `--no-dependencies`, and only Sentry
  is bundled.
- **Hyphens:** cargo turns `-` into `_` in the output file name, so try
  both spellings.
- **Not built yet:** `problem: "it has no build yet: build it first (cargo v5 build)"`.
- **`Program`:** add `elf?: string` (the `.bin` path without its extension,
  when that file exists) for Debug on Sim.
- **`projectRoot`:** also stops at a folder whose `Cargo.toml` is a vexide
  one. A Cargo workspace root with members is out of scope; it says so in
  `problem`.
- **`project()`:** order PROS, then VEXcode, then Cargo.
- **`programForFile`:** `slot_*.base.bin` is refused with "a differential
  upload's base: run its project's build".

### A2. Builds (`src/buildWatch.ts`, `src/runOnSim.ts`)
- **`isProgramBuild`:** also accepts `.../target/<*-vex-v5>/<debug|release>/<name>.bin`,
  but not `slot_*.base.bin`.
- **Watcher:** add a second one,
  `**/target/*-vex-v5/{debug,release}/*.bin`. Keep the existing glob as it
  is: a single `{a,b}` glob covering both layouts gets unwieldy.
- **Log line:** mention `target/*-vex-v5/*/*.bin`.

### A3. Commands and UI
- **Context key:** `v5sim.vexProject` → `v5sim.simProject`, true for a
  VEXcode or vexide project, so the editor-title ▶ Run on Sim also shows in
  Rust projects. Update `package.json` `when` clauses.
- **Run Program on Sim picker:** lists the Cargo project. When `cargo` and
  `cargo-v5` are on PATH and the brain is on Windows USB or the host is
  macOS/Linux, add "Upload this Rust project with cargo v5". That runs
  `cargo v5 upload --slot N` in a terminal, mirroring `prosUpload` and its
  WSL-serial refusal.
- **Explorer context menu:** `.bin` already covers a Rust build. Nothing
  to add.

### A3b. Out-of-date builds: warn first (all project kinds)
Before Run on Sim, Debug on Sim, or an upload of a project's program,
compare the program's mtime with the newest source file:
- PROS and VEXcode: `src/`, `include/`.
- Rust: `src/`, `Cargo.toml`, `Cargo.lock`.

If a source file is newer, warn: "<project>'s build is older than its
source (<file> changed). Build it first?" with these buttons:
- **Build and run:** runs the project's own build in a terminal and waits
  for it to finish.
  - PROS: `pros make`.
  - Rust: `cargo v5 build` (debug profile for Debug on Sim).
  - VEXcode: the VEXcode extension's build command, if it exposes one;
    otherwise this button isn't shown.
  - Then it runs the new build. A failed build stops there.
- **Run anyway:** runs the old build.
- **Cancel.**

Nothing builds without the user choosing it. The after-build offer never
warns, because it fires on a fresh build.

- **Code:** `staleSource(root, program, fs)` in `programs.ts`, returning
  the newest newer file or undefined. Pure, with tests: each kind, ignored
  folders (`bin`, `build`, `target`, `.git`), and a missing `src/`.

### A4. Tests (`test/programs.test.ts`, `test/buildWatch.test.ts`)
- `cargoProject`:
  - each target triple, debug versus release (newest wins);
  - a hyphenated package name;
  - no build;
  - a non-vexide Cargo project (undefined);
  - slot out of range.
- `projectRoot`: finds `Cargo.toml` up to 3 levels up.
- `isProgramBuild`: target paths in, base binaries out.

- If differential fails, document it as unsupported and file an issue.

### B4. GDB bridge: `scripts/v5gdb_bridge.py` and `v5brain.sh --gdb PORT`
The piece `SIMULATOR.md` §5 says is missing ("not in the repo yet").

- **Placement:** it takes the user socket's place in the chain:

  ```
  QEMU v5usb-user.sock  ←→  v5gdb_bridge.py  ←→  v5usb-user-out.sock  ←→  v5usb_pty.py / v5usb_usbip.py
                                   ↕
                         TCP 127.0.0.1:PORT (GDB RSP)   +  TCP PORT+1 (program output, plain)
  ```

- **Brain → PC:**
  - The bridge splits the stream on the COBS delimiter and decodes each
    packet.
  - `d` packets go to the GDB client.
  - `l` packets go to stderr, and so to the V5 Sim log.
  - `u` packets go to the output TCP (decoded) and to `-out.sock`
    (unchanged).
  - Bytes that don't decode go to both outputs as user output.
- **Passthrough:** existing consumers (`pros terminal`, the v5gdb CLI
  over usbip) see the original bytes.
- **PC → brain:** while a GDB client is connected, its bytes go to the
  brain and writes from `-out.sock` are dropped (v5gdb treats all inbound
  bytes as debugger data). With no client, `-out.sock` writes pass through.
- **v5brain.sh:**
  - `--gdb PORT` starts the bridge before the pty or usbip helper and points
    that helper at `v5usb-user-out.sock`.
  - It adds `, GDB localhost:PORT` to the instance line.
  - The default port is 35537 + instance id.
  - It binds 127.0.0.1 only. WSL2 forwards localhost to Windows.
- **Tests:** `scripts/v5gdb_bridge_test.py` (unittest):
  - COBS round trips;
  - frames split across reads;
  - oversize frames;
  - unknown channel;
  - GDB connect and disconnect switching who writes.
  
  Feed it from a recorded user-port trace (`V5USB_TRACE`) of `vexide_gdb`.

### B5. GDB e2e
`scripts/gdb_test.sh`:
- run `v5brain.sh --run vexide_gdb.bin --gdb 35537`;
- `gdb-multiarch -batch` with: `target remote :35537`, `break <fn>`,
  `continue`, `bt`, `info registers pc`, `continue`, a Ctrl-C (interrupt),
  `detach`;
- check the breakpoint hit and the backtrace names.

Repeat with a PROS hot/cold build of the same program, using v5gdb from
its depot.

## Workstream C: Debug on Sim (extension)

### C1. Simulator plumbing
- **`instanceLine.ts`:** parse `GDB localhost:(\d+)` into `Running.gdbPort`.
- **`simInstance.ts`:**
  - `RunOnce` gets `gdb?: boolean`, and the start args add `--gdb`.
  - The port comes from the instance line; it's never assumed.
- **Debug starts on `--usb` ptys** when there's a choice: no Windows COM
  port, so VEXcode's polling can't grab it. Keep `--usbip` if the user set
  `v5sim.usb: usbip`; the bridge passes through either way.

### C2. "V5 Sim: Debug on Sim" (`src/debug/debugOnSim.ts`)
1. **Pick the project:**
   - the open editor's project, else the workspace folder's, else ask;
   - a PROS project (hot/cold or monolith) or a vexide one;
   - a VEXcode project gets "Debugging needs v5gdb, which supports PROS and
     vexide projects".
2. **Check the project uses v5gdb:**
   - Rust: `v5gdb` in `Cargo.toml` dependencies.
   - PROS: `v5gdb` in `project.pros` templates.
   - If not, warn first: "<project> doesn't use v5gdb, which Debug on Sim
     needs. Add it?" with buttons **Add v5gdb**, **Show me how** (opens the
     wiki page) and **Cancel**.
   - **Add v5gdb** makes two changes:
     - **Dependency**, in a terminal so the user sees it:
       - Rust: `cargo add v5gdb`.
       - PROS: `pros c add-depot v5gdb <depot URL>` (skipped if
         `pros c list-depots` already has it), then `pros c apply v5gdb`.
     - **Install call**, as a `WorkspaceEdit` with `needsConfirmation`, so
       VS Code shows its refactor preview and nothing is written until the
       user applies it:
       - Rust: `v5gdb::install(V5Debugger::stdio().stop_motors_on_break(true));`
         as the first line of the `#[vexide::main]` function, plus
         `use v5gdb::prelude::*;`.
       - PROS: `v5gdb::install({.stop_motors_on_break = true});` as the
         first line of `initialize()`, plus `#include "v5gdb/v5gdb.h"`.
       - If the function isn't found (moved, renamed, macros), insert
         nothing and show the snippet to paste instead.
   - **Version gates**, checked before adding: vexide ≥ 0.9.0-alpha.1
     (`Cargo.lock`) and PROS kernel ≥ 4.2.3 (`project.pros`). An older one
     gets a warning naming the upgrade command (`cargo update -p vexide`,
     `pros c upgrade`) and isn't changed.
   - **Then it builds:** after adding, the project needs a build, which
     goes through A3b's warning.
3. **Check it's debuggable** (and A3b's out-of-date warning):
   - Rust: a `debug` profile build, or a warning if only `release` exists
     (no symbols for locals).
   - PROS: `bin/hot.package.elf` / `cold.package.elf` or `bin/monolith.elf`
     exist.
4. **Start the program:** `sim.restart({ program, slot, link, gdb: true })`,
   then wait for `gdbPort` to accept a connection (`waitForPort`, 60 s,
   cancellable progress).
5. **Attach:** `vscode.debug.startDebugging(folder, config)`, with the
   `cppdbg` config from C3.
6. **Program output:** a "V5 program (sim N)" terminal, a `Pseudoterminal`
   reading TCP `gdbPort+1`. It's closed when the debug session ends.
7. **When the debug session ends:** keep the simulator running (the user
   can look at the robot). Offer "Stop simulator" in the session's end
   message, once.

### C3. Building the debug configuration (`src/debug/debugConfig.ts`, no VS Code imports)
- **`debugConfig({ program, elf, coldElf, gdbPath, port, cwd })`** returns
  `cppdbg`:
  - `request: "launch"`, `program: elf`, `MIMode: "gdb"`;
  - `miDebuggerPath: gdbPath`;
  - `miDebuggerServerAddress: "127.0.0.1:<port>"`;
  - `stopAtConnect: true`;
  - `setupCommands`: v5gdb's memory map, plus `add-symbol-file <coldElf>`
    for hot/cold;
  - `cwd`.
- **Which ELF:**
  - vexide: `target/<triple>/<profile>/<name>`;
  - PROS hot/cold: `bin/hot.package.elf` + `bin/cold.package.elf`;
  - PROS monolith: `bin/monolith.elf`.
- **Tests:** unit tests for each kind and for missing files.

### C4. `v5sim` debug type (`package.json` `debuggers`, `src/debug/provider.ts`)
- **Contribution:** `"type": "v5sim"`, with `configurationAttributes` for
  `launch`: `program?` (a project folder or a `.bin`), `slot?`, `gdbPath?`.
  Add snippets and `initialConfigurations` so "Add Configuration…" and an
  empty `launch.json` offer "V5 Sim: Debug on Sim".
- **Provider:** `resolveDebugConfiguration` runs C2's steps 1–4 and returns the `cppdbg` config from C3.
- **Type switch:** confirmed supported by VS Code (see the spike results), so no fallback is needed.
- **Command:** `v5sim.debugProgram` in the V5 Sim menu, the sidebar, the
  editor title (`v5sim.simProject`), and the Command Palette.

### C5. Finding GDB (`src/debug/gdb.ts`)
1. `v5sim.gdbPath` (new setting, `scope: machine`).
2. The PROS toolchain: `<globalStorage>/sigbots.pros/install/pros-toolchain-{windows,macos,linux}/usr/bin/arm-none-eabi-gdb[.exe]`.
3. PATH: `arm-none-eabi-gdb`, `gdb-multiarch`, `gdb`. A plain `gdb` must
   report `arm` support, checked with
   `gdb -batch -ex "set architecture arm"`.

None found: a message with the install line for the OS (from the v5gdb
wiki), and a button that opens the setting.

### C6. Debugger extension
- `cppdbg` comes from `ms-vscode.cpptools` (VS Code). Cursor has
  `anysphere.cpptools`; VSCodium has neither.
- Detect the installed one; if none, offer to install it.
- Don't add it to `extensionDependencies`: it's heavy, and Run on Sim
  doesn't need it.
- VSCodium fallback: "Native Debug" (`webfreak.debug`, `type: "gdb"`,
  `request: "attach"`, `remote: true`, `target: "127.0.0.1:<port>"`).
  `debugConfig` gets a second output shape for it.

### C7. Tests and manual matrix
- **Unit:** `debugConfig`, GDB discovery (fake fs/exec), `instanceLine` with
  GDB.
- **Manual:**

  | Host | Brain | Program | Expect |
  |---|---|---|---|
  | Windows, pty (WSL) | sim | vexide_gdb | break, step, locals, bt, continue, stop |
  | Windows, usbip | sim | PROS hot/cold + v5gdb | same; `pros terminal` still works while not debugging |
  | macOS arm64 | sim | vexide_gdb | same, Homebrew gdb |
  | Windows, pty | sim | VEXcode C++ | clear "needs v5gdb" message |
  | any | sim | v5gdb in project, release build | warning about symbols, still attaches |

## Risks

- **v5gdb is pre-1.0:**
  - Risk: its framing or setup may change.
  - Mitigation: pin the tested version in the docs and test programs; the
    bridge's frame handling sits in one function with recorded-trace tests.
- **Windows GDB reaching WSL's port:**
  - Risk: WSL2 localhost forwarding may be off (`localhostForwarding=false`,
    mirrored networking quirks).
  - Mitigation: test it, and print the WSL address in the error with a
    `v5sim.gdbHost` escape hatch if needed.
- **Pausing the program in GDB:**
  - Risk: the robot sim keeps simulating, so a paused program's motors keep
    their last command.
  - Mitigation: v5gdb's `stop_motors_on_break` covers it; enable it in the
    snippets and docs.
- **VSCodium/Cursor debugger differences (C6):**
  - Mitigation: test Cursor once; VSCodium gets the Native Debug path or a
    documented "not supported yet".

## Decisions (2026-11-20)

1. **Out-of-date builds:** warn first and offer to build, for every project
   kind (A3b). Never build silently.
2. **Adding v5gdb:** Debug on Sim adds v5gdb to the project after a warning,
   and the code edit goes through a preview (C2 step 2).
3. **LLDB:** not planned.
4. **Program Terminal:**
   - **Debug sessions** (simulator started with `--gdb`): it shows the
     bridge's program output (TCP `gdbPort+1`, C2 step 6), because
     `pros terminal` can't share the port with v5gdb.
   - **Otherwise:** `pros terminal`, falling back to `screen`, as now.
   - **Later, 0.5:** consider making the bridge the default, with a PROS
     decoder. That would end the need for PROS or `screen` in WSL.
